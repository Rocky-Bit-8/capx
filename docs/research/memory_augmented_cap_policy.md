# 面向 Code-as-Policy 的反馈记忆与参数级测试时适应

## 研究概述

CaP-X 当前主要让大语言模型生成控制代码，并通过 `goto_pose` 等 API 操作机器人。一个可行的扩展方向是：不训练或微调大模型参数，而是利用相机、深度、末端位姿和关节状态建立反馈记忆，在多轮执行中只对动作参数进行修正。

该方向的核心问题不是简单地保存对话历史，而是建立如下映射：

> 视觉/本体反馈 -> 状态误差与失败类型 -> 可解释的动作参数增量

例如，模型不直接重新生成完整程序，而是输出受约束的修正：

```json
{
  "delta_position": [0.008, -0.003, 0.0],
  "delta_yaw": 0.12,
  "delta_approach": -0.01,
  "reason": "目标在图像中偏右且接触后发生滑移",
  "confidence": 0.72
}
```

控制器随后对原始动作施加边界检查、碰撞检查和 IK 检查，再执行下一步动作。

## 与现有 CaP-X 的关系

当前仓库已经具备若干相关能力：

- multi-turn code generation；
- visual differencing；
- execution history；
- 自动生成和复用 skill library；
- 相机视觉、物体位姿、末端状态和关节状态；
- 参数化的运动和抓取 API。

因此，“给 LLM 增加 memory”“使用抽帧进行多轮反馈”本身并不是充分的新颖性来源。研究贡献应进一步收窄到：

1. 参数级闭环修正，而不是重新生成完整代码；
2. 视觉误差与动作参数增量之间的结构化映射；
3. 视觉反馈和 proprioception 的联合记忆；
4. 相似失败经验的检索、复用和跨任务迁移；
5. 不改变模型参数的测试时适应，并用实验量化其收益。

## 可行性评价

整体可行性较高，但不建议让大模型直接从原始图像和全部关节角度推断修正量。更稳妥的系统结构是：

```text
相机/关节数据
    -> 状态估计与误差提取
    -> 结构化反馈
    -> 检索相似失败案例
    -> LLM 生成或选择有界参数增量
    -> 安全约束、碰撞检查、IK 检查
    -> 执行动作并记录结果
```

结构化反馈可以包括：

- 目标与末端的位置误差；
- 姿态误差和平面内 yaw 误差；
- IK 是否成功；
- 接触、抓取和滑移状态；
- 目标遮挡或视觉置信度；
- 预期位移与实际位移的差异；
- 碰撞、越界和控制器执行错误。

这样可以减少 LLM 直接进行精确几何推理的负担，并保证所有修改都落在安全范围内。

## Memory 设计

每条经验不应只保存“图像 -> 修正参数”，而应保存一次完整的控制 transition：

```json
{
  "task": "pick_cube",
  "object": "red_cube",
  "state_before": {
    "ee_pose": "...",
    "joint_state": "...",
    "object_pose": "...",
    "image_embedding": "..."
  },
  "action": {
    "api": "goto_pose",
    "position": "...",
    "orientation": "...",
    "approach": "..."
  },
  "feedback": {
    "position_error": "...",
    "orientation_error": "...",
    "contact": false,
    "slippage": false,
    "ik_success": true
  },
  "correction": {
    "delta_position": "...",
    "delta_yaw": "...",
    "delta_approach": "..."
  },
  "outcome": "success",
  "confidence": 0.85
}
```

检索应综合考虑任务和物体语义、视觉 embedding、空间误差、当前关节构型、失败类型、控制 API 以及参数范围，而不是只做自然语言相似度匹配。

## 主要技术难点

同一视觉现象可能有多个原因。例如目标在图像中偏右，可能来自末端位置偏差、目标位姿估计错误或相机标定误差；抓取失败可能来自位置、姿态、夹爪宽度、接近方向、未接触或物体滑移。因此应显式区分：

1. 感知误差；
2. 运动规划或 IK 误差；
3. 控制执行误差；
4. 接触和抓取动力学误差；
5. 任务语义或 API 使用错误。

memory 应记录失败分类及其置信度，并允许模型拒绝修正或请求重新感知。否则系统容易把坐标系错误、视觉误检和真正的控制偏差混为一谈。

## 创新性判断

| 研究内容 | 初步创新度 |
| --- | --- |
| 给代码生成 Agent 加历史记录 | 较低 |
| 使用抽帧和视觉差异进行多轮控制 | 中等，已有相关工作和 CaP-X 能力 |
| 视觉与关节反馈联合 prompt | 中等 |
| 只修正动作参数而不重生成代码 | 较高 |
| 学习“反馈类型 -> 参数增量”的可复用记忆 | 较高 |
| 跨任务迁移失败修正经验 | 较高 |
| 不训练模型的持续策略改进 | 有潜力，但必须严格定义和验证 |

更准确的研究定位应是：

> Memory-Augmented Parameter Adaptation for Code-as-Policy Robot Control

或：

> Test-Time Residual Adaptation for Vision-Proprioceptive Code Policies

关键词应突出 `residual adaptation`、`parameter correction`、`episodic memory` 和 `test-time adaptation`，而不是只使用宽泛的 `LLM memory`。

## 实验方案

### Baseline

至少比较以下设置：

1. 单轮 CaP，无反馈；
2. 多轮 CaP，仅视觉反馈；
3. 多轮 CaP，视觉和关节反馈；
4. 普通历史记录，不使用结构化 memory；
5. 结构化 memory，但不检索失败案例；
6. LLM 重新生成完整代码；
7. LLM 只修改动作参数；
8. oracle residual controller，作为上限参考。

### 指标

- 任务成功率；
- 平均修正轮数；
- 每次修正后的误差下降；
- 失败恢复率；
- 碰撞率、越界率和危险动作率；
- LLM 调用次数与推理延迟；
- 新任务上的 zero-shot / few-shot 泛化；
- memory 规模与性能之间的关系。

重点应进行跨场景测试：场景 A 中积累的失败经验，是否能帮助场景 B 的相似任务，而不是只在同一条轨迹上反复修正。

## 最小可行实验

建议先限制问题规模，不直接处理任意代码和完整视频：

1. 选择单一 `goto_pose` 抓取任务；
2. 只允许修正 `dx, dy, dz, dyaw`；
3. 每次动作后读取 RGB-D、末端位姿和关节状态；
4. 提取目标位置误差、末端误差、接触和抓取结果；
5. 检索过去的相似状态和失败类型；
6. 让 LLM 从有限候选增量中选择，或生成有界增量；
7. 对位移、速度、姿态和碰撞设置硬约束；
8. 比较无 memory、普通 history 和结构化 memory。

如果该实验能证明相同类型的失败可以被更快修正，再逐步扩展到姿态、接近距离、抓取方向和跨任务迁移。

## 研究价值与结论

该方向具有较好的工程可行性和研究价值，尤其适合 CaP-X，因为仓库已经提供代码执行、多轮交互、视觉差异、API 抽象和执行日志等基础设施。

真正需要证明的不是“大模型是否能记住历史”，而是：

> 一个由视觉-本体反馈驱动的、可检索的残差动作修正 memory，能否在测试时提高 Code-as-Policy 的样本效率、鲁棒性和迁移能力。

若能在受控任务上完成上述因果对比，并证明经验可以迁移到新场景，该方向可以形成明确的算法贡献，而不仅是 prompt engineering 或日志存储系统。
